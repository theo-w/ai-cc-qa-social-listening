## 1. 一句话价值主张

**用 AI 把客服质量管控和舆情响应从"抽检 + 人工盯"变成"全量检测 + 分级响应 + 闭环复盘 + 线索传递"。**

副标题：AI 质检 — badcase 闭环 × 舆情分级预警 — 快速响应 × 运营看板 — 线索传递

## 2. 问题与机会

| 领域 | 现状 | 代价 |
|---|---|---|
| 客服质检 | 人工抽检覆盖率通常不足 10%，不同质检员标准不一 | 风险样本漏检；问题发现滞后 |
| badcase 复盘 | 发现问题后停留在"扣分/通报"，没有责任人、SLA、复发验证 | 同类问题反复发生，培训与知识库不同步 |
| 舆情监控 | 靠人工盯评论，分级凭感觉，跨品牌/市场联动断层 | P0 事件响应以小时/天计 |
| 运营看板 | 指标口径不统一，发现异常后无法下钻到 case 和责任人 | 周会看数，散会无行动 |
| 线索传递 | 客服/舆情发现的产品问题、商机停留在各自系统 | 跨团队价值流失 |

机会：用"检测 → 分级 → 工单 → 看板 → 线索 → 复盘 → 知识库"一条链路，把质量数据变成可执行动作。

## 3. 目标与非目标

### 3.1 目标（MVP 内必须成立）

1. 质检从"抽检"变"全量检测 + 低置信度人工复核"，覆盖率与准确率可量化。
2. 每个 badcase 有归因、责任人、SLA、状态流转与闭环验证。
3. 舆情分级（P0/P1/P2）有明确触发规则、SOP、响应计时与升级路径。
4. 看板指标有统一口径，异常可一键下钻到 case 列表。
5. 可从质检 case / 舆情预警 / 看板异常一键生成线索，并追踪到跨团队闭环。
6. 以上全部可在本地一键启动、可演示、可复现，评测结果可展示。

### 3.2 非目标（明确不做）

- 不做完整客服工作台/工单系统（不接管真实会话）。
- 不做模型训练平台、不做微调、不追求 SOTA 分类效果。
- 不做全渠道舆情爬虫（MVP 用公开评论导入 + 种子数据）。
- 不做自动处罚、不自动对外发布、不替代公关与法务判断。
- 不做多租户、计费、真实鉴权（演示态用角色切换模拟）。
- 不做真实 LLM 调用（MVP 用确定性规则引擎模拟 AI；保留 Provider 扩展位）。

## 5. 产品原则

- **P1 全量优先，抽检兜底**：默认全量检测，人工只处理低置信度与高风险样本。
- **P2 人工是最终责任**：AI 不直接处罚；低置信度必须复核；误判必须有申诉与留痕。
- **P3 闭环优先于报表**：每个问题都必须有责任人、SLA、下一步动作，否则不算"发现"。
- **P4 分级响应**：影响面决定响应级别，级别决定 SLA、通知对象与权限。
- **P5 线索意识**：一次发现要能变成一条可追踪的跨团队行动。
- **P6 可解释**：每个 AI 判定都带证据（原话、规则、置信度），拒绝"黑箱评分"。
- **P7 演示优先**：MVP 先跑通端到端可演示链路，再谈规模化与替换真实模型。

## 6. 工程原则

- **E1 规格先行**：见 `specs/README.md`；先改规格再改代码。
- **E2 契约优先**：OpenAPI 是前后端唯一契约。
- **E3 单仓多包、边界清晰**：`apps/api`（逻辑与数据）、`apps/web`（界面）、`data`（评测/种子数据）、`docs`（业务附录）互不越界。
- **E4 确定性优先**：MVP 规则引擎 + 置信度；`AI Provider` 接口预留，未来可换真实模型。
- **E5 数据可重置**：任何演示前可一键恢复种子数据，保证可复现。
- **E6 可追溯**：状态变化必须写 timeline（谁、何时、从什么到什么、备注）。
- **E7 零外部依赖**：本地 Node 即可运行，不依赖数据库、消息队列、外部 API。

## 7. 质量门禁

| 门禁 | 要求 |
|---|---|
| 规格 | 每条 P0 需求有可测试验收条件；API 契约可独立实现 |
| 代码 | TypeScript strict 通过；`pnpm build` 成功；无 `any` 泛滥（引擎/契约层禁止） |
| 测试 | 契约测试覆盖所有 P0 端点；核心状态机有单元测试；评测脚本可重复执行 |
| 演示 | 6 条主链路（见 `docs/demo-script.md`）可连续演示，无阻塞性报错 |
| 评测 | 质检准确率 / 舆情情感准确率达标；不达标时报告写明偏差与原因 |

## 9. 术语表

| 术语 | 定义 |
|---|---|
| 对话（Conversation） | 一段坐席与用户的完整会话记录，可来自在线/工单/电话转写 |
| 质检结果（QcResult） | AI 对一条对话的评分、结论、标签与证据集合 |
| 标签（Tag） | 质检维度下的具体问题类型，如服务态度、违规话术等 6 类 |
| 低置信度（Low Confidence） | 整体置信度 < 0.75 的判定，必须人工复核 |
| 人工复核（Review） | 质检员对 AI 判定的确认/改判，是准确率的人工基线 |
| badcase | 经复核确认的负面案例，进入归因、分派、修复、验证的闭环 |
| 归因（Root Cause Category） | 知识缺失 / 话术问题 / 流程问题 / 系统问题 |
| 复发（Recurrence） | 同一根因类别 + 同一标签在闭环后再次出现 |
| 舆情预警（Alert） | 对评论聚合分析后，按 P0/P1/P2 分级生成的响应工单 |
| 分级（P0/P1/P2） | 按影响面与扩散趋势划分的响应级别，决定 SLA 与通知范围 |
| SOP | 标准响应流程：确认 → 口径 → 对外 → 记录 → 复盘 |
| 线索（Clue） | 从质检/舆情/看板发现的可交给产研、品牌、市场的行动项 |
| SLA | 服务承诺时限，超时在界面与看板中高亮 |
| 评测集（Dataset） | 带人工标注的固定样本集，用于计算准确率/误报/漏报并版本化复测 |
| 置信度（Confidence） | 0-1，规则引擎对本次判定的自评；用于决定是否转人工 |
| EvalRun | 一次在固定评测集上的完整评测，产出指标、混淆矩阵与错例 |

## 10. 风险登记册

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 无真实数据，演示说服力不足 | 中 | 合成场景数据 + 明确标注"合成评测集 v0.1"，附数据生成脚本 |
| R2 | 规则引擎与标注口径不一致，指标不达标 | 高 | 评测规范先冻结；数据与引擎同源规则设计；每周复测并调整 |
| R3 | 演示时间有限 | 中 | 6 条主链路脚本化，一键 reset，覆盖核心价值而不是全部功能 |
| R4 | 前端演示态数据操作后状态混乱 | 中 | 所有写操作经 API + 落库文件 + 自动刷新；提供 reset |
| R5 | 过度设计拖慢 MVP | 高 | 严格按 `008-tasks.md` 的 P0 范围；P2 全部后置 |
| R6 | 隐私与合规问题 | 中 | 种子数据全部虚构；脱敏规则写入 NFR；不采集真实用户数据 |
