# SDD 规范 · QCC 客服质量运营工作台

> 本文件定义本项目的 **Spec-Driven Development（规格驱动开发，下称 SDD）** 工作方式与文档标准。
> 一句话：**先写可验收的规格，再写代码；代码必须能追溯到规格条目；评测结果就是验收证据。**

版本：v0.1.0 ｜ 维护人：Lead ｜ 更新日期：2026-11-03 ｜ 状态：生效

---

## 1. 为什么这个项目需要 SDD

| 问题 | SDD 的应对 |
|---|---|
| 三个模块（质检 / 舆情 / 看板+线索）需求密度高，聊天式需求必然丢信息 | 每条需求有唯一 ID、来源、验收条件 |
| AI 参与开发，需要人和 AI 读同一份上下文 | 规格即共享上下文，任务卡只引用规格 ID，不复述 |
| 产品岗位作品集要证明"能把模糊业务变成可验收系统" | 产出物里有一整套从 PRD 到任务、测试、评测的追溯链 |
| Demo 容易做成"能点但不可信" | 指标口径、评测集、误报/漏报统计是规格的一部分，不是装饰 |

## 3. 阶段与门禁

```
Phase 0 章程/PRD ──Gate0──> Phase 1 规格 ──Gate1──> Phase 2 澄清/评测口径 ──Gate2──>
Phase 3 技术方案（架构/数据/API/UI） ──Gate3──> Phase 4 任务分解 ──Gate4──>
Phase 5 实现 ──Gate5──> Phase 6 验证/复盘 ──Gate6──> 发布 v1.0
```

| 门禁 | 通过标准（缺一不可） | 检查清单 |
|---|---|---|
| Gate 0 | 目标与非目标明确；成功指标可度量；PRD 每条需求有编号 | `checklists/spec-review.md` 第 1 节 |
| Gate 1 | 每条 P0 需求有 Given/When/Then 验收；无不可测形容词 | `checklists/spec-review.md` 第 2 节 |
| Gate 2 | 所有歧义有结论并记录；评测集与指标口径冻结（版本化） | `checklists/evaluation.md` |
| Gate 3 | API 契约可被第三方按文档实现；数据模型能支撑所有 FR；页面状态齐全 | `checklists/spec-review.md` 第 3 节 |
| Gate 4 | 每个任务有写作用域、依赖、验收、责任角色；关键路径无环 | `checklists/spec-review.md` 第 4 节 |
| Gate 5 | 构建通过；契约测试通过；端到端演示路径可走通；无 P0/P1 缺陷 | `checklists/release-readiness.md` |
| Gate 6 | 指标达成或偏差有解释；演示脚本可复现；复盘结论回写规格 | `checklists/release-readiness.md` + 评测报告 |

> **门禁原则：没通过就停在原地补，不带着未决问题进入下一阶段。** MVP 允许裁剪范围，不允许裁剪验收。

|---|---|---|---|

| `NFR-` | 非功能需求 | `NFR-PERF-02` | 是 |

| `MET-` | 指标定义 | `MET-QC-ACC` | 是 |
| `API-` | 契约端点编号（与 OpenAPI 对应） | `API-QC-04` | 是 |

## 5. 需求写法

### 5.1 功能需求模板

```markdown
### FR-QC-03 AI 质检结果生成
- 优先级：P0
- 来源：PRD-QC-02、PRD-QC-05
- 用户故事：US-QC-02
- 描述：作为质检负责人，我希望系统对导入的对话自动给出评分与违规标签，以便只把低置信度样本交给人复核。
- 规则：
  1. 每条对话必须生成恰好一条质检结果（幂等，重跑覆盖不重复）。
  2. 每条命中标签必须携带证据（消息序号 + 原文片段 + 规则 ID + 置信度）。
  3. 整体置信度 < 0.75 时 `needsReview=true`，进入人工复核队列。
- 验收：
  - Given 一条含"你眼瞎吗"的对话，When 执行质检，Then `attitude` 标签命中且证据指向该消息。
  - Given 置信度 0.62，When 生成结果，Then 出现在待复核列表且复核前不计入准确率分子。
- 接口：API-QC-02、API-QC-03
- 测试：TEST-QC-04、TEST-QC-07
```

### 5.2 禁用表述

> "友好""合理""尽量""适当""高效""体验好"——出现即退回重写。必须换成可观察、可计数、可判定的描述。

### 5.3 优先级

| 级别 | 定义 | 门禁要求 |
|---|---|---|
| P0 | 演示主链路上的环节，缺失即不可演示 | 必须有验收 + 测试 |
| P1 | 影响可信度/闭环完整性的能力 | 有验收，测试尽力覆盖 |
| P2 | 体验优化、次要筛选/导出 | 记录即可，允许 MVP 后实现 |

## 6. 变更管理

1. **先改规格，再改代码。** 任何行为变化必须先落到 `specs/` 或 `docs/`，再进入实现；紧急修复允许代码先行，但须在 24h 内回写规格并在 changelog 标注。
2. **版本语义**：`v0.x` 草稿期（本阶段）；`v1.0` MVP 冻结版；之后 Minor = 兼容新增，Major = 契约破坏性变更。
3. **变更分级**：
   - Patch：文案/样式/内部重构（不需要评审）
   - Minor：新增接口字段、新筛选、新页面状态（需自查 Gate 相关项）
   - Major：状态机、指标口径、契约破坏（需更新追溯矩阵 + 重新跑评测）
4. 每份文档头部保留「变更记录」表；根目录 `CHANGELOG.md` 记录 MVP 里程碑。

## 7. 契约优先与合作规则

- `specs/contracts/openapi.yaml` 是前后端**唯一接口契约**。实现与契约不一致时，**以契约为准**；确需变更时先改契约、再改两端。
- 数据模型变化必须同时更新：`004-data-model.md`、`openapi.yaml`、`specs/fixtures/` 样例。
- 前后端并行开发只通过契约 + fixtures 协作，不靠口头约定。
- 运行时代码不得依赖外部网络服务（演示环境可离线运行）。

## 8. 评测即验收

- 每个 P0 功能需求必须能对应到 `007-evaluation-spec.md` 中的指标或 `specs/checklists/release-readiness.md` 中的可执行验证步骤。
- 评测集是**版本化数据**（`data/README.md`），标签口径变更视为 Major 变更，须重跑历史评测。
- 发布声明必须附最近一次评测结果（`EvalRun`）；未达标而发布，须写明偏差与原因，禁止静默。

## 9. 任务卡格式（AI/人协作最小单元）

```markdown
### T-API-03 质检结果查询接口
- 目标：实现 API-QC-02/03，返回契约定义的 ConversationDetail 结构
- 写作用域：apps/api/src/routes/qc.ts、apps/api/src/services/qc.ts
- 依赖：T-API-01（服务骨架）、T-DATA-01（种子数据）
- 验收：pnpm test 通过；curl 样例与 specs/fixtures/qc-detail.json 结构一致
- 不做：不做前端页面；不改契约；不动 data/ 下文件
```

规则：一张卡一个可独立验收的产出；写作用域必须与其它并行卡不重叠；依赖必须指向已存在的任务 ID。

## 10. 模板

### ADR 模板

```markdown
### ADR-NN 标题（决策一句话）
- 状态：提议 / 已接受 / 已废弃
- 背景：要解决什么问题、有哪些约束
- 选项：A / B / C，各自代价
- 决策：选了哪个
- 理由：为什么（含被否选项的否决原因）
- 后果：正面 / 负面 / 需要后续观察的点
```

### 缺陷模板

```markdown
- 编号：BUG-NN
- 现象：可复现的具体表现（含页面/接口/输入）
- 期望：引用 FR/TEST 编号
- 复现步骤：1. 2. 3.
- 影响：用户可见后果 + 严重级别（P0-P3）
- 根因：一句话（修复前必须能回答）
```

## 12. 完成定义（Definition of Done）

一个需求"完成"必须同时满足：

- [ ] 规格条目存在且通过对应 Gate 检查
- [ ] 契约（OpenAPI / 数据模型）同步更新
- [ ] 实现与验收条件逐条对应，有测试或可复现的演示步骤
- [ ] 相关页面状态齐全（加载 / 空 / 错误 / 无权限）
- [ ] 追溯矩阵中的链路完整：PRD → FR → API/UI → Task → Test
- [ ] 若影响指标：最近一次 EvalRun 结果已附上
