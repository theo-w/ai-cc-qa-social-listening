# 舆情预警处置 SOP

> 适用：QCC Workbench MVP 舆情模块。评论按「主题 × 日期」聚合成簇后生成预警，按 P0/P1/P2 分级处置。
> 依据：`specs/007-evaluation-spec.md` §5（聚合与回放口径）、§6（分级规则）、§6.3（SLA）；`specs/004-data-model.md` §3.8（预警字段）、§4.5（责任人路由）、§5.2（状态机）；动作契约见 `specs/005-api-contract.md` §3.6。
> 原则：**先止损、再定责、后复盘**；所有处置动作在系统留痕（timeline），对外口径必须经品牌/主管确认。

## 1. 角色与职责

| 角色 | 负责人 | 职责 |
|---|---|---|
| 预警值班 | 客服运营（轮值） | 监控新预警、30 分钟内确认、初步判级与分派 |
| 品牌口径 | 江岚 | 外挂/充值类对外口径、媒体与社区回应 |
| 产研接口 | 周野 | 版本/Bug 类技术核实、修复排期 |
| 客服主管 | 陆川 | 客服/活动/其他类处置、流程与培训联动 |
| 质检组长 | 沈言 | P0 复盘、badcase 联动与质量结论 |

## 2. 评论聚簇与级别口径（007 §5、§6）

1. 聚簇键：`primaryTopic + publishedAt 日期`；同主题同一天为同簇（演示数据每簇 4–12 条）。
2. 单条级别 `expectedLevel`：P0/P1/P2/none，按 §3 规则由金标给出；引擎预测用 `severity`（小写），口径一致。
3. 聚合升级：簇内负面 **≥ 8 → P0**；**3–7 → 至少 P1**；**1–2 → 至少 P2**；0 → 无升级。
4. 簇级别 = `max(单条最高级别, 聚合升级级别)`；预警按簇级别发起。
5. 匹配键 `(topic, date)`：预测预警与期望预警按此键匹配，级别一致计正确。

**演示数据示例（可直接用于演练）**：`充值 · 2026-11-01` 簇共 10 条且全部负面，单条最高仅 P2，负面 ≥ 8 触发聚合升级 → 簇级别 **P0**（唯一由聚合升级产生的 P0 簇）。处置时不得因「单条都不高」而降级。

## 3. 单条级别判定规则（007 §6.1，标注与引擎共用）

| 级别 | 判定条件（满足其一） | 典型信号 |
|---|---|---|
| P0 | 负面 **且** 高危主题（外挂/充值/版本）**且** 出现高危信号词；或明确资损/数据丢失 | 回档、封号误封、扣款不到账、无法登录、大面积、集体、维权、投诉、12315、媒体曝光、退款潮 |
| P1 | 负面 **且** 主题（版本/Bug/活动/客服/充值）**且** 描述明确影响；无 P0 信号 | 闪退、卡顿、进不去、黑屏、掉线、异常、失败、延迟、拖延、态度差、敷衍、排队、没人处理、无法使用、加载不出、领取失败、匹配失败 |
| P2 | 负面或中性的抱怨、建议、体验反馈；无 P0/P1 信号 | 「活动少一点」「客服回复有点慢」「希望优化建模」 |
| none | 正面、中性无行动价值、噪声（广告/灌水/无关） | 「好玩，推荐」「BUG 修复速度很快」 |

## 4. 分级响应 SLA 与责任人（007 §6.3、004 §4.5）

| 级别 | 首次响应 SLA | 默认责任人 | 通知范围 |
|---|---|---|---|
| P0 | **30 分钟** | 江岚（品牌）+ 陆川（主管）+ 周野（产研） | 品牌/主管/产研 + 质检组长 |
| P1 | **2 小时** | 按主题路由（见下表） | 品牌/主管 |
| P2 | **24 小时** | 按主题路由 | 观察池（无需单独通知） |

| 舆情主题 | 默认责任人 | 说明 |
|---|---|---|
| 外挂 / 充值 | 江岚（品牌） | 涉及品牌声誉、支付与退款 |
| 版本 / Bug | 周野（产研） | 技术核实、修复排期 |
| 客服 / 活动 / 其他 | 陆川（客服主管） | 服务流程、活动规则、杂项 |

> SLA 超时未确认的预警在列表与看板标红；`firstResponseAt` 在「确认」或「直接升级」动作时写入，用于计算响应时长。

## 5. 处置流程（004 §5.2 状态机）

```text
new ──acknowledge──▶ acknowledged ──respond──▶ responding ──resolve──▶ resolved
 │                        │                        │
 └──────escalate──────────┴──────escalate──────────┴──▶ escalated ──resolve──▶ resolved
                                                             └─respond──▶ responding（降级继续处理）
```

| 步骤 | 动作（API type） | 前态 → 后态 | 必填 | 时间要求 |
|---|---|---|---|---|
| 1 确认 | `acknowledge` | new → acknowledged | note | P0 ≤30min，P1 ≤2h，P2 ≤24h |
| 2 处理 | `respond` | acknowledged → responding | note（对外口径/联动动作） | 确认后立即开始 |
| 3 升级 | `escalate` | new/acknowledged/responding → escalated | note | 见 §6 升级条件 |
| 4 解决 | `resolve` | responding/escalated → resolved | note | 按事件进度 |
| 5 记录 | `comment` | 不变 | note | 关键节点随时 |

**处置动作要求**：

- 确认时必须写明：簇的 `topic/date`、评论条数、负面条数、簇级别、是否聚合升级、初判影响范围。
- 处理中至少每 2 小时更新一次进展（P0 每 30 分钟更新），直到 resolved。
- resolved 前必须完成：根因初判、用户可见口径已发布（如需）、线索/工单已创建或明确不需要。

## 6. 升级条件（满足其一即 escalate）

1. 簇级别为 P0，或处置中发现资损/数据丢失/大面积无法登录。
2. 涉及监管（12315/投诉）、媒体曝光、集体维权、法律风险字样。
3. 2 小时内需要产研修复决策，但责任人无法决策。
4. 同主题连续 3 天出现新簇且未收敛（趋势恶化）。
5. 对外口径出现对外传播风险（社区/媒体已出现二次转载）。

## 7. 沟通模板

### 7.1 预警确认（内部，写入 acknowledge 的 note）

```text
【确认】{topic} · {date} 簇，共 {n} 条评论，负面 {neg} 条，簇级别 {level}（聚合升级：是/否）。
初判影响：{影响范围/资损情况}；建议动作：{产研排查/对外口径/客服话术}；责任人：{owner}。
```

### 7.2 升级通知（内部，写入 escalate 的 note）

```text
【升级】{topic} · {date} 簇由 {oldLevel} 升级为 escalated。
原因：{触发条件}；当前评论 {n} 条、负面 {neg} 条；涉及来源：{steam/taptap/...}。
需决策事项：{对外口径/修复时限/补偿方案}；建议会议时间：{时间}。
```

### 7.3 对外回复要点（品牌/主管确认后使用）

```text
1. 已关注到玩家关于 {问题} 的反馈，第一时间启动排查；
2. 当前进展：{已定位原因/修复中/预计 X 时间恢复}；
3. 对受影响玩家的处理：{补偿/退款/恢复方案，按官方公告口径}；
4. 后续进展将通过官方公告/社区持续同步，感谢监督。
```

## 8. 关闭条件与复盘

**可关闭（resolve）**：

- 根因已定位且修复/口径已发布，簇内新增负面评论连续 24 小时收敛；
- 涉及资损的已完成补偿/退款方案说明；
- 关联线索/工单已闭环或有明确结论；
- 质检侧若发现服务问题，已转 badcase（见 `docs/badcase-template.md`）。

**复盘（P0 必做，P1 建议做）**：

| 复盘项 | 内容 |
|---|---|
| 时间线 | 首条评论 → 预警生成 → 确认 → 升级 → 解决，各节点耗时 |
| 判级准确性 | 单条级别与簇级别是否正确，是否漏掉聚合升级 |
| SLA | 是否在 30min/2h/24h 内确认，超时原因 |
| 处置有效性 | 对外口径是否被二次传播，负面是否收敛 |
| 改进项 | 规则/流程/产品/培训的后续动作与责任人 |

## 10. 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 只看单条级别，忽略聚合升级 | 漏报 P0（如充值 11-01 簇） | 必须按负面条数计算聚合级别后取 max |
| 用 `severity` 大写 P0 判级 | 与契约不一致 | 引擎预测用 `severity` 小写；金标/展示用 `expectedLevel` 大写 |
| 确认后不写 note/不更新进展 | 无法计算响应时长与复盘 | 每个动作都写 note，至少 2 小时一次进展 |
| P0 未通知产研 | 修复延迟、舆情扩大 | P0 默认通知 江岚+陆川+周野 |
| 舆情问题直接开 badcase 替代预警 | 状态机混用、SLA 错乱 | 预警走本 SOP；服务问题另开 badcase |
| 解决后不收敛观察 | 负面回潮 | resolved 前确认 24 小时无新增集中负面 |
