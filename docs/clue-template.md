# 线索模板与分发规范

> 适用：QCC Workbench MVP 线索模块。把质检/舆情/看板中发现的**可行动问题**整理成线索，分发给产研、品牌、市场或客服团队，并跟踪到闭环。
> 依据：`specs/004-data-model.md` §3.9（Clue 字段）、§4.5（线索接收路由）、§5.3（状态机）；动作契约见 `specs/005-api-contract.md` §3.7、§3.8。
> 原则：**一条线索只解决一个问题**，必须可回跳来源、可执行、可验收。

## 1. 线索与 badcase / 预警的区别

| 对象 | 解决的问题 | 流转 | 典型来源 |
|---|---|---|---|
| 舆情预警（SentimentAlert） | 舆情事件本身的响应 | new → acknowledged → responding → resolved | 评论聚簇 |
| Badcase | 服务侧问题（知识/话术/流程/系统） | open → in_progress → pending_verify → closed | 质检违规/复核改判 |
| **线索（Clue）** | 跨团队改进机会（产品需求、品牌动作、市场机会、客服优化） | draft → routed → accepted/rejected → closed | 质检/舆情/看板/坐席 |

同一个舆情事件可以同时产生「预警」与「线索」：预警负责止损与对外口径，线索负责推动产研/品牌/市场/客服的长期改进。

## 2. 字段填写要求（004 §3.9）

| 字段 | 必填 | 填写要求 |
|---|---|---|
| `id` | 系统生成 | `clue-0001`，不可手改 |
| `title` | 是 | 一句话，≤ 30 字，写「对象 + 问题」，如「外挂与误封集中爆发」 |
| `description` | 是 | 背景（数据证据）+ 建议动作，2–5 句；写明期望对方做什么 |
| `sourceType` | 是 | `qc` / `sentiment` / `dashboard` / `agent` |
| `sourceRef` | 是 | `{ type, id, label }`，可点击回跳，如 `{ "type": "alert", "id": "alt-0002", "label": "外挂 · 10-29 集中负面" }` |
| `target` | 是 | `product`（产研）/ `brand`（品牌）/ `market`（市场）/ `cs`（客服） |
| `priority` | 是 | `high` / `medium` / `low`，按 §5 标准判定 |
| `status` | 系统写 | `draft` / `routed` / `accepted` / `rejected` / `closed` |
| `owner` | route 时必填 | 接收方负责人，按 §4 路由 |
| `createdBy` | 是 | 建单人 |
| `evidence` | 是 | 至少 1 条证据：原文引用、指标数字、簇统计（如「10 条评论、负面 10、聚合升级 P0」） |
| `outcome` | close 时必填 | 处理结果/交付物/拒绝理由 |
| `timeline` | 系统写 | 每次动作追加 `{ at, by, type, note, from, to }` |

## 4. 接收方路由（004 §4.5）

| target | 默认负责人 | 适合的线索 |
|---|---|---|
| `product`（产研） | 周野 | Bug/版本/系统缺陷、支付回调、外挂对抗、功能需求 |
| `brand`（品牌） | 江岚 | 外挂/充值类舆情、对外口径、品牌声誉、补偿方案 |
| `market`（市场） | 程雨 | 活动设计、玩家口碑、竞品对比、增长机会 |
| `cs`（客服） | 陆川 | 话术/流程/排队/培训、坐席执行力问题 |

> 一条线索只能有一个 `target`；跨团队事项拆成多条线索并在 description 中互相引用。

## 5. 优先级判定标准

| 优先级 | 判定条件（满足其一） | 时限建议 |
|---|---|---|
| high | P0 舆情簇/资损/大面积无法使用/监管或媒体风险；影响面 ≥ 30% 用户或涉及付费 | 24 小时内受理并给排期 |
| medium | P1 舆情簇/明确功能异常但有替代路径/服务质量集中反馈 | 3 个工作日内受理 |
| low | 体验建议、单点问题、观察类机会 | 进改进池，双周评审 |

优先级由建单人初判，接收方可调整一次并在 timeline 说明理由；调整后不得低于来源级别隐含的下限（P0 事件线索最低 high）。

## 6. 线索创建示例（可直接用于演示）

```markdown
### 线索
- id：clue-0001
- 标题：外挂与误封集中爆发，需产研与品牌联合响应
- 目标团队：brand
- 优先级：high（判定依据：P0 簇、提及 12315/媒体曝光、付费玩家受影响）
- 来源类型：sentiment
- 来源引用：type=alert id=alt-0002 label=外挂 · 2026-10-29 集中负面
- 建单人：沈言          创建时间：2026-10-30T09:20:00+08:00

#### 背景与数据证据
2026-10-29 外挂主题评论 10 条全部负面，簇级别 P0；4 条单条 P0 提及「封号误封」「12315」「媒体曝光」；
另有 2 条为正常玩家误封申诉，存在补偿与口径需求。

#### 建议动作
1. 产研：本周内上线外挂检测策略 v2，给出误封申诉绿色通道。
2. 品牌：发布对外口径，说明误封处理与补偿方案。

#### 验收标准（可度量）
- [ ] 7 天内该主题新增负面评论 ≤ 2 条/天
- [ ] 交付物：外挂策略说明公告 + 误封申诉通道上线

#### 处理结果（close 时必填）
- outcome：
- 交付物链接/单号：
```

## 7. 状态机与流转规则（004 §5.3、005 §3.8）

```text
draft ──route──▶ routed ──accept──▶ accepted ──close──▶ closed
                    │                    ▲
                    └──reject──▶ rejected ──close──▶ closed
```

| 动作（API type） | 前态 → 后态 | 必填 | 校验规则 |
|---|---|---|---|
| `route` | draft → routed | `owner` | 目标团队与 `owner` 路由一致，不一致需说明 |
| `accept` | routed → accepted | `owner`（可覆盖） | 接收方确认排期/负责人 |
| `reject` | routed → rejected → closed | `note`（理由） | 理由必须具体，不能只写「不归我们」 |
| `close` | accepted → closed | `outcome` | 必须写交付物或结论，验收项逐条勾选 |
| `comment` | 任意 → 不变 | `note` | 记录进展 |

补充规则：

- `rejected` 允许一次申诉：建单人可在 7 天内以 `comment` 补充证据并申请重新 route；二次拒绝即归档。
- `closed` 后不得重开；同类问题再次出现应新建线索并引用历史 id。
- 所有流转写入 timeline，看板「线索闭环率」按 `closed / total`（total=0 返回 0，002 FR-SYS-005）计算（口径见 `docs/metric-dictionary.md`）。

## 8. 线索质量验收清单

- [ ] 标题能看出「为了谁、解决什么问题」
- [ ] 有可回跳来源（`sourceRef` 可点击）
- [ ] 有数据证据（条数/占比/指标值），不是主观感受
- [ ] 建议动作是接收方能执行的具体动作
- [ ] 验收标准可度量（时间 + 指标/交付物）
- [ ] 一条线索只有一个目标团队
- [ ] 优先级与来源事件级别匹配

## 9. 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 线索写成「请关注/请优化」 | 接收方无法执行，最终石沉大海 | 写清动作 + 交付物 + 时限 |
| 证据只写「用户抱怨很多」 | 无法核实，易被拒绝 | 附条数、负面数、簇级别、原文引用 |
| 同一问题拆成多条低质量线索 | 看板指标失真、重复沟通 | 合并同源问题，跨团队再拆 |
| 拒绝理由写「不归我们管」 | 无法申诉、无法改进 | 写明归属判断依据或转派建议 |
| close 时 outcome 为空 | 无法计算闭环率、无法复盘 | 写清交付物/结论，验收项逐条确认 |

## 10. 模板维护

- 字段以 004 §3.9 为准；动作与校验以 005 §3.8 为准；本模板随契约版本同步更新。
- 建议每周抽样 5 条高频目标团队线索，复盘「创建→受理→闭环」时长与拒绝原因。
